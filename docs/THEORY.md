# 71類完全平行：理想情境，不是實测

71個獨立分支同時開始、沒有競爭或排隊時：

$$T_{total}=T_{prefix}+\max_{i=1}^{71}(T_i)+T_{assembly}$$

不能將整體時間直接除以71。實際同一張GPU的batch會增加總運算量，不等同71份獨立硬體。

## 以已量到資料估算

| 輸入 | 平均時間 | 取自 |
|---|---:|---|
| 冷前綴準備 | 0.704217s | 6K／71路 |
| 單類HTTP回應代理值 | 0.240622s | 32K／4路，不含client排隊 |
| 機率計算與組裝 | 0.000649s | 6K／71路 |

假設每類都維持約240.6ms，完全重疊且無額外競爭：

`0.704217 + 0.240622 + 0.000649 = 0.945488s`

加原測試中途metrics開銷約 **0.950623s**；前綴完成後約0.24s。
**以平均值代替未知最慢分支、混用兩種配置的測量做代理，屬樂觀情境，不是硬體理論下限或速度承諾。**
公式與來源值可由 [theory.json](../results/theory.json) 和原始回覆重算。

## 目前為何仍需3.48s？

目前仍有20032個未快取tokens，預算2048時，單按token工作量至少需ceil(20032/2048)=10個排程步驟。
這只是預算下限，不是已量到的forward次數；排程、快取狀態容量與kernel計算還有其他成本。

若能精確共享前綴尾端，可避免249×71=17679 tokens重算，剩2353 tokens；這是88.25%的token減量假設，非相同幅度的時間改善。
混合架構快取對齊尚未修改。提高batch預算、改善共享或換推論實作都仍是待驗證方案。

**實測最新：總平均3.481s，分支平均2.771s。理想值約0.95s，尚未達成。**
